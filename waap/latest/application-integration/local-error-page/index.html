Replace backend error pages

Aero WAAP can replace the error response of a backend with a local error page stored on the appliance. The client then receives your page instead of the one the backend application generated. Optionally, the status code sent to the client can be overwritten as well.

Why replace backend error pages

Error pages generated by application servers and frameworks are written for developers, not for the public. They often reveal more than they should:

  • Stack traces and exception messages that expose class names, file paths, source code lines or SQL statements.
  • Product names and versions of the application server, framework or libraries, which help an attacker find known vulnerabilities.
  • Internal details such as hostnames, IP addresses, database names or the layout of the backend infrastructure.

An attacker can provoke such errors on purpose, for example with malformed input, and use what they reveal to plan further attacks. This is known as information disclosure through error messages (CWE-209 ).

Replacing these responses with a local error page:

  • prevents information disclosure, because the backend's error content never reaches the client,
  • makes fingerprinting harder, because every backend behind Aero WAAP answers errors with the same page, whatever product it runs on,
  • gives a consistent user experience, with one branded error page across all applications of a virtual host, instead of a different default page per backend,
  • covers errors you do not control, for example the default pages of a third-party product or of a backend that is temporarily misconfigured.

Overwriting the status code goes one step further: it hides which kind of error happened (see When to overwrite the status code ).

Replace the backend's error pages on a virtual host

  1. Under Local Files > Error Pages , create or upload the error page. Choose the Content Type that matches the content, for example text/html for a browser application or application/json for an API.
  2. Open the virtual host and go to the Error Pages & Maintenance Pages tab.
  3. In the Error Pages section, click "Add error page".
  4. Select the Response Status to replace, for example 5xx for every server error.
  5. Select the Local Error Page created in step 1.
  6. Optionally set an Overwrite Status Code .
  7. Optionally restrict the entry with an Additional Header Condition , for example to replace only HTML responses.
  8. Save, then create a revision and deploy it to apply the change.

Hint

Start with an entry for 5xx. Server errors are the most likely to contain stack traces and internal details.

When to overwrite the status code

If Overwrite Status Code is not set, the client receives the backend's original status code together with your page. Setting it hides the real status, for example:

  • Answer all server errors with the same code. Replace 5xx with 500 so that a client cannot tell a failing backend (502), an overloaded one (503) or a timeout (504) apart.
  • Hide whether a resource exists. Replace 403 with 404 so that a client cannot tell a protected resource from a missing one. This makes it harder to enumerate resources such as admin pages or user accounts.

Warning

Clients, monitoring and caches rely on status codes. Overwrite them only where you know the effect:

  • Do not overwrite 401 on routes that use HTTP authentication. Browsers and API clients need the 401 to ask for credentials.
  • API clients may handle status codes differently, for example retry on 503 but not on 500.
  • Monitoring and alerting that counts status codes sees the overwritten code, not the original one.

To help users report a problem without exposing details, include the request ID through a response variable :

<h1>Something went wrong</h1>
<p>Please try again later. If the problem persists, contact support with this reference:
%REQ(X-REQUEST-ID)%</p>

Replace HTML error pages only, keep API errors

An application that serves both a website and a JSON API may return structured error responses that its API clients need. Add a header condition so that only HTML responses are replaced:

Field Value
Response Status 5xx
Local Error Page error.html
Additional Header Condition on
Type Response
Name Content-Type
Match Type Contains
Value text/html
Field Value
Response Status 5xx
Local Error Page error.html
Additional Header Condition on
Type Response
Name Content-Type
Match Type Contains
Value text/html

Entries with header conditions are checked first, so you can add a second 5xx entry without a condition, with a JSON page, for all other responses. See Which entry applies .

Good to know

  • Only the listed status codes are replaced. Error pages can be configured for 400, 401, 403, 404, 405, 500 to 505, and the classes 4xx and 5xx. Responses with other status codes are passed through unchanged.
  • Maintenance pages take precedence. On routes with an active maintenance page , no error page is served.
  • An error page in use cannot be deleted. Remove it from every virtual host first.
  • Combine with other protections. Error pages replace the response body. To keep response headers from revealing the backend's software, see Security headers and Header manipulation .
